# Operations ERP product contract

Build a production-oriented, multi-tenant operations ERP using only the Python
standard library. The product must be runnable from a clean checkout without
network access or third-party services.

## Required package and interfaces

Create an `erp` package with these modules:

- `erp/service.py` exports `ERPService`, `AuthorizationError`,
  `ConflictError`, `NotFoundError`, and `ValidationError`.
- `erp/app.py` exports `create_app(database_path)` and returns a WSGI
  application. `GET /health` must return HTTP 200 JSON with `status: "ok"`.
- `erp/cli.py` provides an executable administration CLI.

`ERPService(database_path)` must persist all state in SQLite and provide:

- `create_organization(name, owner_email, password)`
- `login(organization_id, email, password)`
- `create_user(token, email, password, role)`
- `create_vendor(token, name, email)`
- `create_purchase_order(token, idempotency_key, vendor_id, lines)`
- `approve_purchase_order(token, purchase_order_id)`
- `receive_inventory(token, idempotency_key, purchase_order_id)`
- `get_inventory(token, sku)`
- `create_invoice(token, idempotency_key, vendor_id, purchase_order_id, amount_cents)`
- `pay_invoice(token, idempotency_key, invoice_id)`
- `get_invoice(token, invoice_id)`
- `list_audit_events(token)`
- `health()`

Return JSON-serializable dictionaries. Identifiers and token formats are your
choice, but they must be opaque and collision-resistant.

## Business rules

- Organizations are strict security tenants. No identity, vendor, order,
  inventory, invoice, ledger, or audit data may cross tenant boundaries.
- Roles are `admin`, `manager`, and `auditor`. Admins and managers may run the
  procurement workflow. Auditors are read-only and may inspect invoices,
  inventory, and audit records.
- Passwords must be salted and hashed with a standard-library password KDF.
  Plaintext passwords must never be stored.
- A purchase order contains one or more `{sku, quantity, unit_cost_cents}`
  lines. Quantities and costs are positive integers, SKUs are non-empty, and
  the returned total is computed by the service.
- Only an approved purchase order may be received. Receiving is atomic,
  idempotent, and increases inventory exactly once.
- An invoice must reference the same vendor and purchase order, use a positive
  amount, and may not exceed the purchase-order total.
- Paying an invoice is atomic and may happen only once. It creates exactly one
  durable ledger entry. Concurrent attempts with different idempotency keys
  must yield one success and one conflict, never two payments.
- Reusing an idempotency key with the identical operation and payload returns
  the original result. Reusing it with a different payload raises
  `ConflictError`.
- Invalid or failed operations must leave all balances, inventory, workflow
  state, and idempotency records unchanged.
- Mutating operations and denied authorization attempts must create durable,
  tenant-scoped audit events.

## Deliverables

- A documented `README.md` with architecture, security/transaction decisions,
  CLI and WSGI usage, and test commands.
- A valid `pyproject.toml` with an ERP CLI entry point.
- At least three meaningful test modules covering service behavior,
  authorization/tenant isolation, persistence/idempotency, and concurrency.
- The complete implementation must pass `python -m unittest discover -s tests
  -v`, `python acceptance.py`, and compilation without warnings or network
  access.

Do not edit this file or `acceptance.py`. Do not leave placeholders, TODO-only
paths, skipped core behavior, fake in-memory persistence, or tests that merely
assert constants.
